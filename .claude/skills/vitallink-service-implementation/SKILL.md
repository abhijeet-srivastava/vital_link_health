# VitalLink service implementation

This skill carries the architecture and conventions agreed for the VitalLink Readings & Alerting
service so every later change lands the same way. The service is also the template for the rest of
the platform: new services copy its shape (ingest → outbox → Kafka → idempotent consumers → read APIs).

## Start every task here

1. Identify which part of the system the task touches and read only the matching reference:

   | Task touches | Read first |
   | --- | --- |
   | Components, topics, data flow, deployables | `references/architecture.md` |

   | Why something is the way it is; open questions | `references/decisions.md` |

2. Look at the existing code before writing new code; extend existing ports and adapters instead of
   adding parallel ones.
3. If the task conflicts with a rule below or with `references/decisions.md`, stop and say so
   instead of silently diverging. If it touches an **open clinical decision**, implement behind a
   flag and flag it in the PR description.

## The system in one paragraph

Devices POST batches of readings to **ingest-api**, which authenticates the device key, checks the
device↔patient binding at `measured_at`, inserts readings with `ON CONFLICT DO NOTHING RETURNING`,
writes a `readings.ingested` outbox row for the new rows only, commits and returns `202`. A CDC
relay (Debezium; a `SKIP LOCKED` poller locally) publishes outbox rows to Kafka keyed by
`patient_id`. **alert-worker** evaluates readings in batches into alert *episodes* (one unresolved
alert per patient and measure), records each breaching reading in `alert_occurrence`, and announces
new episodes and severity upgrades through its own outbox. The notifier turns each change into one
notification per coach and channel. **query-api** serves latest readings, time ranges and the coach
queue from Redis and read replicas. Stack: Java 21, Spring Boot 3, PostgreSQL 16, Kafka, Redis 7,
Flyway, Testcontainers, Resilience4j, Caffeine.

## Non-negotiable rules

Each rule exists because breaking it causes a duplicate alert, a lost alert, a stalled morning
ingest, or a PHI incident.

1. **The database enforces correctness.** Every write that can be retried has a natural unique key
   and uses `ON CONFLICT` or a conditional `UPDATE`. Redis or in-memory checks are only fast
   pre-checks. No distributed locks, no "check then insert" without a constraint behind it.
2. **Events only through the outbox.** Any change that must be announced writes an `outbox_event`
   row in the same transaction. Never call a Kafka producer inside a business transaction.
   `event_id` is a UUIDv7 generated by the application.
3. **Every consumer is idempotent.** Use the natural key of its side effect (`alert_occurrence`,
   `notification`); fall back to `processed_event(consumer, event_id)` only when no natural key
   exists. Commit Kafka offsets only after the DB commit.
4. **Ingest never waits on downstream work.** No alert evaluation, LLM call, notification or
   cross-service call on the ingest request path. Redis updates after commit are best-effort.
5. **Everything is patient-scoped.** Kafka key = `patient_id` (device events: `device_id`); hot
   queries filter on `patient_id`; nothing may require a cross-patient join on the hot path. This
   is what makes sharding possible later.
6. **Time-series tables are partitioned by time.** The partition key is part of every unique key;
   read with keyset pagination on `(measured_at, reading_uuid)`, never `OFFSET`. Times are
   `TIMESTAMPTZ` / `Instant` in UTC; keep `measured_at` (device) and `received_at` (server) apart.
7. **State changes are conditional updates.** `UPDATE … WHERE id = ? AND version = ? AND status IN
   (legal sources)`; zero rows → `409` with the current state. No `SELECT` then `UPDATE` without a
   lock or version.
8. **Severity comes from rules; AI is advisory.** Severity = most severe threshold band crossed.
   LLM output may set `ai_priority` only, behind a timeout, circuit breaker and fallback, and never
   on the ingest or evaluation path.
9. **PHI stays minimal.** Logs, metrics labels and Kafka payloads carry IDs and values only - never
   names, contact details or free text. Every PHI read and every alert state change writes
   `audit_log`. Coaches see only patients in their current `care_assignment`.
10. **Durability is not traded for speed.** Keep `synchronous_commit` on. Get throughput from
    batching and set-based SQL, not from weaker guarantees.
11. **Write paths use explicit SQL** (Spring `JdbcClient`/`JdbcTemplate` or jOOQ) so `ON CONFLICT`,
    `RETURNING`, `unnest` batches and `SKIP LOCKED` are visible in review. No JPA/Hibernate on
    ingest, evaluator or notifier paths.

## Workflow for a new feature or change

1. **Design delta** - write 3-5 lines: which tables, events, endpoints and guards change, and which
   rule above each change relies on. Put it in the PR description.
2. **Migration** - Flyway `V<yyyymmddhhmm>__<verb>_<object>.sql`; run the checklist in
   `templates/sql/migration_checklist.sql`. Never edit an applied migration.
3. **Domain and ports** - pure Java in `domain/`; interfaces in `ports/` (see
   `templates/java/Ports.java`).
4. **Adapters** - SQL in `persistence/`, Kafka in `messaging/`, HTTP in `api/`.
5. **Events** - new event type: add it to the `outbox_event.event_type` CHECK, give the payload a
   `schema_version`, document it in `references/architecture.md`, keep it IDs-only.
6. **Consumers** - start from `templates/java/BatchAlertEvaluator.java`: batch path plus per-event
   fallback, offsets after commit, DLQ after bounded retries.
7. **API** - `/v1/...`, RFC 7807 errors, keyset cursors, `If-Match` for state changes, OIDC scopes
   checked in the controller and enforced again by row-level security.
8. **Tests** - the must-have list in `references/testing.md` for anything touching ingest,
   duplicates, alerts or access control.
9. **Observability** - latency per stage, consumer lag, rows per commit, and a business metric for
   the feature (see `references/performance-and-scaling.md`).
10. **Docs** - update the affected reference file and add a line to `references/decisions.md`
    when a decision changes.

## Review checklist (use on your own diff before finishing)

- [ ] Every retried write has a DB-enforced natural key; replaying the same input changes nothing.
- [ ] Events are written to the outbox in the same transaction as their data.
- [ ] Kafka offsets are committed after the DB commit; poison messages go to a DLQ after N retries.
- [ ] No unbounded query: every list endpoint is keyset-paginated and patient- or coach-scoped.
- [ ] New unique keys on partitioned tables include the partition key.
- [ ] Repeat-update columns on hot rows are unindexed (HOT updates) where possible.
- [ ] State transitions use `version` + legal source states; `409` path tested.
- [ ] No PHI in logs, metric labels, exception messages or event payloads.
- [ ] PHI reads and state changes write `audit_log`; access checked against `care_assignment`.
- [ ] External calls (LLM, SMS, push) have timeout, retry budget, circuit breaker and fallback.
- [ ] CRITICAL alerts are never delayed by digests, confirmation rules or non-critical backlog.
- [ ] Tests from `references/testing.md` added for the touched area and passing.

## Code layout

```
vital_link_health/
  readings-alerting/
    ingest-api/        # HTTP write path, device auth, outbox writer
    alert-worker/      # evaluator, notifier, escalation scheduler, AI triage consumer
    query-api/         # latest, range, coach queue, summaries
    common/
      domain/          # Reading, Alert, ThresholdRule, Severity, Measure ... (no framework code)
      ports/           # interfaces from templates/java/Ports.java
      persistence/     # JdbcClient/jOOQ adapters, SQL kept next to the adapter
      messaging/       # outbox relay (local), Kafka config, event DTOs with schema_version
    db/migration/      # Flyway
    load/              # k6 scripts
  docker-compose.yml   # postgres, kafka, redis, services, seed data
```

Adapt to what already exists in the repo; the boundaries (domain free of frameworks, SQL in
adapters, one deployable per scaling profile) matter more than the folder names.

## Open clinical decisions - do not settle in code

Implement behind configuration, default to the safer behaviour, and call them out in the PR:

- An acknowledged alert that rises to CRITICAL returns to `OPEN` and restarts escalation.
- Readings older than 90 days are rejected with `422 READING_TOO_OLD`.
- Patients in several programs without an override get the most conservative default.
- Confirmation rule (`confirm_n` / `confirm_window`) and daily digests are off unless enabled per
  program or patient by a clinician. CRITICAL is always immediate.
